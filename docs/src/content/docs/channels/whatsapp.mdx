## Overview

Jina Connect supports WhatsApp Business API through two BSP (Business Solution Provider) adapters:

| BSP | Adapter | API |
|---|---|---|
| **Meta Direct** | `MetaDirectAdapter` | Meta Graph API v18+ |
| **Gupshup** | `GupshupAdapter` | Gupshup Enterprise API |

## Setup

<Steps>

1. **Configure BSP credentials**

   Set environment variables based on your BSP:

   <Tabs>
     <TabItem label="Meta Direct">
       ```ini
       WHATSAPP_ENABLED=True
       META_PERM_TOKEN=your-permanent-access-token
       META_APP_SECRET=your-app-secret
       META_WEBHOOK_VERIFY_TOKEN=your-verify-token
       ```
     </TabItem>
     <TabItem label="Gupshup">
       ```ini
       WHATSAPP_ENABLED=True
       GUPSHUP_BASE_URL=https://api.gupshup.io
       GUPSHUP_EMAIL=your-account-email
       GUPSHUP_PASSWORD=your-account-password
       ```
     </TabItem>
   </Tabs>

2. **Create a WhatsApp App** via API or admin

   ```bash
   curl -X POST http://localhost:8000/wa/v2/apps/ \
     -H "Authorization: Bearer <token>" \
     -H "Content-Type: application/json" \
     -d '{
       "name": "My WhatsApp App",
       "bsp": "META",
       "phone_number": "+1234567890",
       "waba_id": "your-waba-id"
     }'
   ```

3. **Register webhook URL** with your BSP

   Every app has its own callback URL, carrying an opaque identifier that names
   it. Read the pair to configure — URL and verify token — from the app:

   ```bash
   curl http://localhost:8000/wa/v2/apps/<app-id>/webhook-setup/ \
     -H "Authorization: Bearer <token>"
   ```

   ```json
   {
     "wa_app": "12",
     "bsp": "META",
     "callback_url": "https://your-domain.com/wa/v2/webhooks/meta/whk_Xq3…/",
     "identifier_hint": "whk_Xq3aB9cd…",
     "verify_token": "your-verify-token",
     "verify_token_scope": "deployment",
     "verify_token_configured": true
   }
   ```

   Paste `callback_url` into the **Callback URL** field of the client's own Meta
   App Dashboard (or Gupshup app settings) and `verify_token` beside it. The
   endpoint needs the `wa_app.manage` permission: the URL is a setup credential,
   because whoever holds it can post at that app's receiver.

   | BSP | Per-app webhook URL |
   |---|---|
   | Meta | `https://your-domain.com/wa/v2/webhooks/meta/<webhook-identifier>/` |
   | Gupshup | `https://your-domain.com/wa/v2/webhooks/gupshup/<webhook-identifier>/` |

   <Aside type="caution" title="The unsuffixed URL is single-app">
   The older shared paths — `/wa/v2/webhooks/meta/` and
   `/wa/v2/webhooks/gupshup/`, with no identifier — still work exactly as before,
   so an upgrade never requires re-registering a URL that is already configured.
   They authenticate against the deployment-wide `META_APP_SECRET` and verify
   token, which means they cannot tell two clients' apps apart: **use them for at
   most one app, and never share one between clients.** A deployment hosting
   several client-owned Meta apps gives each one its own per-app URL above.
   </Aside>

   `verify_token_scope` reports whose token the handshake checks. It is
   `deployment` today — one token for the whole instance; per-app verify tokens
   are tracked separately. A setup screen should show the token it is given
   rather than assuming.

</Steps>

## Templates

WhatsApp requires pre-approved message templates for business-initiated conversations.

### Template Lifecycle

```
DRAFT → PENDING → APPROVED → (PAUSED/DISABLED)
                 → REJECTED
                 → FAILED
```

### Template Types

| Type | Description |
|---|---|
| `TEXT` | Plain text message |
| `IMAGE` | Image with optional caption |
| `VIDEO` | Video with optional caption |
| `DOCUMENT` | Document attachment |
| `CAROUSEL` | Multi-card carousel |
| `CATALOG` | Product catalog |
| `PRODUCT` | Single product |

### Template Categories

| Category | Description |
|---|---|
| `AUTHENTICATION` | OTPs and verification codes |
| `MARKETING` | Promotional messages |
| `UTILITY` | Transactional updates (order confirmations, shipping) |

### API Endpoints

| Method | Endpoint | Description |
|---|---|---|
| `GET` | `/wa/v2/templates/` | List all templates |
| `POST` | `/wa/v2/templates/` | Create a new template |
| `GET` | `/wa/v2/templates/{id}/` | Get template details |
| `PUT` | `/wa/v2/templates/{id}/` | Update template |
| `DELETE` | `/wa/v2/templates/{id}/` | Delete template |

## Messages

### Sending Messages

```bash
# Send a template message
curl -X POST http://localhost:8000/wa/v2/messages/ \
  -H "Authorization: Bearer <token>" \
  -H "Content-Type: application/json" \
  -d '{
    "phone": "+1234567890",
    "template_name": "order_update",
    "template_params": {"1": "ORD-123", "2": "shipped"}
  }'
```

### Message Statuses

```
PENDING → SENT → DELIVERED → READ
                            → FAILED
```

### Webhook Events

Inbound messages and status updates arrive via webhooks:

| Event Type | Description |
|---|---|
| `message` | Incoming message from user |
| `status` | Delivery status update (sent, delivered, read, failed) |
| `template_status` | Template approval status change |

#### How a delivery is attributed to an app

On a **per-app URL** the path decides: the identifier is resolved to one app in a
single indexed lookup, and the body is only read afterwards. Nothing the payload
claims can move an event to another app.

On the **legacy shared URL** the body decides, as it always has:
`metadata.phone_number_id` first, then `entry[0].id` (the WABA) when the payload
carries no number.

A delivery to an identifier no app owns is answered `200 {"status": "ignored",
"reason": "unknown_webhook_identifier"}` and nothing is written. The `200` is
deliberate: Meta throttles delivery to the whole deployment on non-200
responses, so one client's stale URL must not slow every other client's events
down. Such rejections are counted per BSP per day, and the identifier is never
written to a log in full — only a short prefix.

#### How a delivery is authenticated

Meta signs every webhook body with `X-Hub-Signature-256`: an HMAC-SHA256 over the
raw bytes, keyed on the **app secret of the app that sent it**. Whoever verifies
a delivery therefore has to hold that app's secret; Meta offers no delegated
alternative.

So the secret is chosen per app:

1. the app's own secret (`meta_app_secret`, stored encrypted and write-only
   through the API) when it has one — this is what lets several client-owned Meta
   apps, each with a different secret, be verified on one deployment;
2. the deployment-wide `META_APP_SECRET` otherwise, which is how a single-app
   install has always worked and continues to.

There is no path that skips verification. A delivery that cannot be verified is
dropped rather than ingested, and answered `200` with a reason:

| `reason` | What happened | Where to look |
|---|---|---|
| `invalid_signature` | The signature did not match the secret in use — commonly a rotated app secret, or a URL registered against the wrong app | The client's app secret in the Meta App Dashboard |
| `app_secret_not_configured` | The app the URL names has no secret stored, and no deployment-wide secret to fall back on | That client's onboarding — store their `meta_app_secret` |
| `missing_app_secret` | The legacy shared URL was used on a deployment with no `META_APP_SECRET` set | The deployment's own configuration |
| `malformed_signature_header` | The `X-Hub-Signature-256` header was absent or not a `sha256=` digest | Whatever is posting — genuine Meta traffic always signs |

Every one of those is an HTTP `200`, for the same throttling reason as above, so
the reason code and the per-app daily counters behind it are the only places a
dropped delivery is visible. A client whose secret rotates keeps sending events
that keep failing, and nothing in the response says so.

Secrets and signature digests are never written to a log. Log lines record only
which *scope* of secret ran — `secret_scope=app` or `secret_scope=deployment` —
which is also how a half-finished rollout is spotted: an app still reading
`deployment` is not yet separable from any other app on that shared secret.

## Subscriptions

Subscribe to webhook events programmatically:

```bash
curl -X POST http://localhost:8000/wa/v2/subscriptions/ \
  -H "Authorization: Bearer <token>" \
  -H "Content-Type: application/json" \
  -d '{
    "name": "Order Status Webhook",
    "webhook_url": "https://your-app.com/webhooks/wa",
    "events": ["message", "status"]
  }'
```

<Aside type="tip">
  Templates are automatically synced with your BSP every 2 minutes via a Celery cron job. You can also manually trigger a sync from the admin panel.
</Aside>
