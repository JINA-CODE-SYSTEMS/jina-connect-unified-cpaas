## Overview

Jina Connect uses **JWT (JSON Web Tokens)** for REST API authentication and **API Keys** for MCP server access.

## JWT Authentication

### Obtain a Token

```bash
curl -X POST http://localhost:8000/token/ \
  -H "Content-Type: application/json" \
  -d '{
    "email": "user@example.com",
    "password": "your-password"
  }'
```

**Response:**
```json
{
  "access": "eyJhbGciOiJIUzI1NiIs...",
  "refresh": "eyJhbGciOiJIUzI1NiIs..."
}
```

### Token Lifetimes

| Token | Lifetime | Algorithm |
|---|---|---|
| **Access** | 90 days (configurable via `ACCESS_TOKEN_LIFETIME`) | HS256 |
| **Refresh** | 180 days | HS256 |

### Refresh a Token

```bash
curl -X POST http://localhost:8000/refresh/ \
  -H "Content-Type: application/json" \
  -d '{
    "refresh": "eyJhbGciOiJIUzI1NiIs..."
  }'
```

### Using the Token

Include the access token in the `Authorization` header:

```bash
curl http://localhost:8000/tenants/ \
  -H "Authorization: Bearer eyJhbGciOiJIUzI1NiIs..."
```

### Which organisation the token is scoped to

`/token/` optionally takes an `X-ACCESS-KEY` header naming which of **your own**
organisations to scope the token to. Without it, your first organisation is used.

```bash
curl -X POST http://localhost:8000/token/ \
  -H "X-ACCESS-KEY: <an access key for an organisation you belong to>" \
  -H "Content-Type: application/json" \
  -d '{"username": "you@example.com", "password": "your-password"}'
```

A key for an organisation you are **not** a member of is refused with
**401 `User does not belong to this tenant`**. There is no superuser exemption to
this: to look at another organisation, use
[View as Organisation](/jina-connect-unified-cpaas/api/impersonation/).

## View as Organisation (impersonation)

A platform superuser can obtain a **read-only, 15-minute, non-refreshable,
audited** token scoped to any organisation, so support questions can be answered
from what the customer sees — without needing anything from the customer.

```bash
curl -X POST http://localhost:8000/impersonate/42/ \
  -H "Authorization: Bearer <superuser access token>"
```

See [View as Organisation](/jina-connect-unified-cpaas/api/impersonation/) for
the full endpoint reference, the limits enforced on the token, what clients
should show while a session is active, and what replaced the removed
`X-ACCESS-KEY` cross-organisation path.

## API Keys

API keys (`TenantAccessKey`) are used for:
- MCP server tool calls
- External system integrations
- Server-to-server communication

Create API keys via the admin panel or API:

```bash
curl -X POST http://localhost:8000/tenants/tenant-access-keys/ \
  -H "Authorization: Bearer <token>" \
  -H "Content-Type: application/json" \
  -d '{"name": "My Integration Key"}'
```

API keys resolve to a specific `(Tenant, TenantWAApp)` pair.

## User Management

| Method | Endpoint | Description |
|---|---|---|
| `GET` | `/users/user/` | List users / Get current user |
| `POST` | `/users/user/` | Register new user |
| `PATCH` | `/users/user/{id}/` | Update user profile |

## REST Framework Auth Classes

The DRF configuration accepts both JWT and Basic auth:

```python
REST_FRAMEWORK = {
    'DEFAULT_AUTHENTICATION_CLASSES': [
        'rest_framework_simplejwt.authentication.JWTAuthentication',
        'rest_framework.authentication.BasicAuthentication',
    ],
}
```

<Aside type="caution">
  Basic auth is enabled for development convenience. In production, prefer JWT only and ensure `DEBUG=False`.
</Aside>
