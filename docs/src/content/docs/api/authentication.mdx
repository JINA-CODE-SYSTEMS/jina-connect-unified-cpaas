## Overview

Jina Connect uses **JWT (JSON Web Tokens)** for REST API authentication and **API Keys** for MCP server access.

## JWT Authentication

### Obtain a Token

```bash
curl -X POST http://localhost:8000/token/ \
  -H "Content-Type: application/json" \
  -d '{
    "email": "user@example.com",
    "password": "your-password"
  }'
```

**Response:**
```json
{
  "access": "eyJhbGciOiJIUzI1NiIs...",
  "refresh": "eyJhbGciOiJIUzI1NiIs..."
}
```

### Token Lifetimes

| Token | Lifetime | Algorithm |
|---|---|---|
| **Access** | 90 days (configurable via `ACCESS_TOKEN_LIFETIME`) | HS256 |
| **Refresh** | 180 days | HS256 |

### Refresh a Token

```bash
curl -X POST http://localhost:8000/refresh/ \
  -H "Content-Type: application/json" \
  -d '{
    "refresh": "eyJhbGciOiJIUzI1NiIs..."
  }'
```

### Using the Token

Include the access token in the `Authorization` header:

```bash
curl http://localhost:8000/tenants/ \
  -H "Authorization: Bearer eyJhbGciOiJIUzI1NiIs..."
```

## View as Organisation (impersonation)

A platform superuser can obtain a **read-only, time-boxed** token scoped to any
organisation, so support questions can be answered from what the customer sees.

```bash
curl -X POST http://localhost:8000/impersonate/42/ \
  -H "Authorization: Bearer <superuser access token>"
```

**Response:**
```json
{
  "access": "eyJhbGciOiJIUzI1NiIs...",
  "expires_at": "2026-09-12T10:45:00+00:00",
  "expires_in": 900,
  "read_only": true,
  "organisation": { "id": 42, "name": "Acme Ltd" },
  "impersonated_by": { "id": 7, "username": "ops_admin" },
  "session_id": 18
}
```

There is **no refresh token** — the session ends when the access token expires
(15 minutes) or when it is exited:

```bash
curl -X POST http://localhost:8000/impersonate/end/ \
  -H "Authorization: Bearer <impersonation token>"
```

The returned token carries `impersonated_by` (the real user's id),
`impersonated_by_username`, `impersonated_tenant_name` and `read_only: true`
alongside the usual `tenant_id`. Clients should show a persistent banner
whenever `impersonated_by` is present.

<Aside type="caution">
  Every non-safe HTTP method (`POST`, `PUT`, `PATCH`, `DELETE`) is refused with
  **403** while the token is in use — including direct API calls, and including
  a second `/impersonate/` call. WebSocket connections are refused outright,
  since a socket has no method to refuse. `POST /impersonate/end/` is the one
  exception. Every session writes a `users.ImpersonationSession` audit row
  naming the real user; deleting that row invalidates the token.
</Aside>

## API Keys

API keys (`TenantAccessKey`) are used for:
- MCP server tool calls
- External system integrations
- Server-to-server communication

Create API keys via the admin panel or API:

```bash
curl -X POST http://localhost:8000/tenants/tenant-access-keys/ \
  -H "Authorization: Bearer <token>" \
  -H "Content-Type: application/json" \
  -d '{"name": "My Integration Key"}'
```

API keys resolve to a specific `(Tenant, TenantWAApp)` pair.

## User Management

| Method | Endpoint | Description |
|---|---|---|
| `GET` | `/users/user/` | List users / Get current user |
| `POST` | `/users/user/` | Register new user |
| `PATCH` | `/users/user/{id}/` | Update user profile |

## REST Framework Auth Classes

The DRF configuration accepts both JWT and Basic auth:

```python
REST_FRAMEWORK = {
    'DEFAULT_AUTHENTICATION_CLASSES': [
        'rest_framework_simplejwt.authentication.JWTAuthentication',
        'rest_framework.authentication.BasicAuthentication',
    ],
}
```

<Aside type="caution">
  Basic auth is enabled for development convenience. In production, prefer JWT only and ensure `DEBUG=False`.
</Aside>
